## 1. Problem framing

The Sprint-2 demo (2026-04-21) leaned on `MockVideoCallView` with `DEMO_MODE` on and a hard-coded `DemoPeerPool`. The video, the peer data, the "matchmaking" animation, and the Trust Gate were all local simulations. For the final write-up to be coherent, v1.1 must deliver:

- **Live matchmaking** — two users actually pair up via Firestore (even if video stays mocked on Appetize).
- **A matching algorithm** — not round-robin through a static pool.
- **Trust Score with teeth** — rewards, decay, and a user-visible recovery path.
- **A visible conversation aid** — icebreaker prompts at session start.
- **A transcript artifact** — post-call transcript (Whisper pivot) as an honest surface for the "speech-to-text" promise.
- **Credibility hygiene** — automated tests and removal of committed secrets, fixing two of the three Code Quality deductions from the Sprint-2 grade.
- **Real feedback data** — a small friends+family pilot, reported honestly as "informal."

## 2. What this spec is *not*

Explicit exclusions to prevent scope drift and to protect the Traceability grade:

- **No AI real-time video moderation.** The Sprint-1 report explicitly marked this as future work. Claiming it now would create a report-vs-code mismatch and surface on grading. It stays in the "Future work" section with a credible-but-unimplemented design sketch.
- **No formal CSUF pilot.** A sanctioned study needs consent processes beyond the 3-week window. The pilot is reported as "informal friends+family (n≈8)."
- **No real-time speech-to-text during the call.** On Appetize, there is no live microphone; the call view runs without one. Real-time Apple `Speech` integration on device can't be demoed honestly. The pivot is a post-call transcript surface instead.
- **No migration off `DEMO_MODE`.** The `Daily` SDK import fails to link without Daily.co credentials wired at build time. `DEMO_MODE` stays ON; matchmaking becomes real while video stays mocked.

## 4. Subproject designs

### A. Icebreaker prompts at session start

**Goal:** Show a conversation-starter prompt as a pill overlay on the call view for the first 12 seconds of every session.

**Design:**

- `IcebreakerService.swift` — `static let pool: [Icebreaker]` with ~30 CSUF-flavored prompts (categories: `general`, `campus`, `interests`). `Icebreaker` is `struct { let id: UUID; let category: Category; let text: String }`. Picking is deterministic by session-id hash so the same two users see the same prompt — avoids the awkward "what are *you* looking at?" mismatch.
- When interests are known for both users (Subproject B+C landed), prefer an icebreaker whose category matches the top shared interest. Fall back to `general`.
- UI: a dismissable glass pill at the top of `MockVideoCallView` that fades out after 12s. Tappable to refresh (pick another) up to 3 times per session.

**Why this scope:** Tiny code, high demo visibility, zero backend dependency, testable with pure XCTest.

### B. Interest-based matching score

**Goal:** Replace round-robin peer selection with a score function, so "we built a matching algorithm" is an honest claim.

**Design:**

- `MatchScorer.swift` — pure struct, no I/O. Public API:
  ```swift
  struct MatchScore { let total: Double; let breakdown: [String: Double] }
  enum MatchScorer {
      static func score(current: User, candidate: User, now: Date = .init()) -> MatchScore
  }
  ```
- Score components (0–100 total):
  - **Interest Jaccard overlap ×50** — `|A ∩ B| / |A ∪ B|` over the `interests` field already on `User`.
  - **Trust proximity ×25** — `1 - |currentTrust - candidateTrust| / 100`, clamped [0,1]. Pairs users of similar trust; avoids matching a verified senior with a brand-new unverified account.
  - **Account-age proximity ×15** — soft bucket (same year/month/week/fresh).
  - **Report-count penalty ×10** — `max(0, 1 - reportCount/5)`.
- Returned `breakdown` map is *only* for tests and debug UI. Production flow uses `total`.
- Integration: `StartChattingView` ranks `DemoPeer` pool (extended with synthetic interests per peer) by the same scorer, so the demo flow visibly picks a more-relevant peer first. `MatchmakingService.findExistingMatch` ranks candidates in the queue the same way.

**Why this scope:** Pure function, trivially unit-testable, the biggest "we built an algorithm" win-per-hour in the whole roadmap.

### C. Live matchmaking (Firestore queue + real pairing)

**Goal:** Replace the `DemoPeerPool` fake in `StartChattingView` with a real Firestore queue so two actual users pair up. Video still renders via `MockVideoCallView` (no real Daily.co on Appetize), but each user sees **the other real user's profile**, not a peer from a static list.

**Design:**

- **Queue doc shape:** `matchmaking_queue/{uid}` with `uid`, `joinedAt`, `status`, `displayName`, `interests`, `trustScore`, `gender`, `showMe`, `lastHeartbeat`.
- **Heartbeat:** client updates `lastHeartbeat` every 10s while in queue. `addToQueue` reaps stale entries (`lastHeartbeat > 30s ago`) on read.
- **Match decision:** when user enters queue, they read other waiting entries whose `showMe` compatibility with this user matches, then score them with `MatchScorer`, pick highest-scoring, then run a Firestore transaction to move both entries to `matched`. Transaction guarantees a candidate isn't double-matched.
- **Session doc:** `sessions/{sessionID}` = `{ participants: [uidA, uidB], createdAt, mode: "mock" | "daily", roomURL?, status: "pending|active|ended" }`. Both clients listen.
- **Video:** with `mode: "mock"`, both clients open `MockVideoCallView` with the other user's name/photo/interests. With `mode: "daily"` (future — post-Appetize), `roomURL` is populated and clients open `DailyVideoCallView`.
- **Firestore rules:** restrict `matchmaking_queue/{uid}` write to `uid == request.auth.uid`. Restrict `sessions/{sid}` read to participants.
- **Fallback:** if the queue is empty after 15s, fall back to the synthetic `DemoPeerPool` so single-user testing still works. Honest — the mock path is a lobby-empty fallback, not the primary experience.

**Why this scope:** This is the "replace demo simulated call" ask, scoped to what ships on Appetize without Daily.co credentials. The *matching* is real; only the *video rendering* stays mocked.

### D. Trust Score reward + recovery path

**Goal:** Trust Score must change based on user behavior, not just stay at the account-creation value. Low-trust users must have a user-visible way to rebuild their score.

**Design:**

- **Reward events** (persist to `trustEvents/{eventID}`):
  - `positiveSessionCompleted`: +2 (mutual Like in `PostSessionFeedbackView`)
  - `neutralSessionCompleted`: 0
  - `reportedBySomeone`: −8
  - `reportedSomeone` (valid): +1
  - `profileCompleted`: +4 (bio+photo+interests+gender+showMe all set)
  - `emailVerified`: +10 (existing, formalized)
  - `weeklyDecay`: −1 per week of inactivity, floor 0
- **Recovery path** — shown when `trustScore < 50`:
  - `TrustRecoveryView.swift` — list of tasks with check states: "Complete your profile," "Verify your email," "Add 3+ interests," "Chat without being reported for 3 sessions." Each task, when checked, calls the reward event and recalculates.
  - Entry point: `StartChattingView.blockedScene` gets a "Rebuild your score" button instead of only "Go back."
- **Recomputation:** `TrustScoreManager.applyEvent(uid, kind)` writes the event, recalculates the full score from scratch (accumulates all events + base), and updates `users/{uid}.trustScore` + `trustScores/{uid}`. All recomputation client-side; deferred to Cloud Functions in the "Future work" section.

**Why this scope:** "Reward model" + "recovery path" in one subproject. Makes the Trust Score visibly *do something*, which the Sprint-2 demo couldn't show because scores never moved.

### E. Post-call Whisper transcript (pivoted speech-to-text)

**Goal:** Surface a transcript of the call on the `PostSessionFeedbackView`.

**Honest constraint:** On Appetize there is no live mic, so we cannot record real audio. The transcript service is stubbed with synthetic transcripts generated from the icebreaker prompt + both names, plus a real HTTP shape that production can flip on.

**Design:**

- `TranscriptService.swift`:
  ```swift
  enum TranscriptService {
      static func transcribe(sessionID: String, audioURL: URL?) async throws -> Transcript
  }
  ```
- When `audioURL` is nil (Appetize path): return a synthetic 4-6 turn transcript built from the session's icebreaker prompt.
- When `audioURL` is present (production path): POST to a `TRANSCRIPT_ENDPOINT` env var, which in production will be a Cloud Function wrapping OpenAI Whisper. Stub with a `URLSession` that hits a `!DEMO_MODE`-gated URL.
- UI: add a `TranscriptRow` section to `PostSessionFeedbackView` collapsed by default, expandable with a "Show transcript" disclosure.
- **Final report copy:** "In v1.1 the transcript is generated client-side from a synthetic transcript service for demo builds; a Cloud Function wrapping OpenAI Whisper is specified in `TranscriptService.swift` and ready to wire in production." This is honest traceability.

**Why this scope:** Gives "speech-to-text" a real code surface, no dependency on platform hardware we don't have.

### F. Tests + security cleanup

**Goal:** Address the Sprint-2 Code Quality deductions: singleton overuse (partial), no automated tests (fixable), `GoogleService-Info.plist` committed (critical).

**Design:**

- **XCTest target** added to `project.yml`: `ToodlesTests`.
- **Unit tests** for:
  - `MatchScorerTests` — pure function, ~8 cases covering Jaccard edge cases, trust proximity edges, report penalty, all-zero input.
  - `TrustScoreManagerTests` — score calculation from synthetic user doc (stubbed Firestore reads via protocol injection), reward event accumulation, decay.
  - `IcebreakerServiceTests` — pool size, deterministic pick per session id, category filtering.
- **Security cleanup:**
  - Add `Toodles/Resources/GoogleService-Info.plist` to `.gitignore`.
  - `git rm --cached Toodles/Resources/GoogleService-Info.plist` — removes from future commits while leaving local file.
  - Add `Toodles/Resources/GoogleService-Info.plist.example` — a committed template with empty values and instructions.
  - **Manual action Danny must take** (documented in commit message + README): **rotate the Firebase API key in Firebase Console** because the previous key was in git history and must be assumed compromised. Current exposure window ends at rotation.
- **Singleton mitigation:** add protocol abstractions (`AuthManaging`, `FirestoreServicing`) so tests can inject stubs without ripping out the existing `.shared` calls. Doesn't fully solve the "singleton overuse" critique but makes the code testable, which is the actionable part.

**Why this scope:** Tests close the "no automated tests" deduction. The `.gitignore` fix + rotation reminder closes the committed-secret deduction. Singleton refactor is deferred — it's a bigger rewrite than the remaining time justifies.

### G. Friends+family pilot materials

**Goal:** Ship real feedback data that can be cited in the final report without overclaiming.

**Design:**

- `docs/pilot/recruit-template.md` — SMS/iMessage template to invite 8-10 friends ("Hey, I'm shipping a capstone app — would you test it for 10 minutes and fill out a form?"). Honest — no incentive beyond a thank-you.
- `docs/pilot/consent.md` — plain-language disclaimer: "This is an academic project. Your data stays in Firestore and will be deleted after 2026-05-31. We'll share aggregate feedback in the final write-up; no individual statements will be quoted without your permission."
- `docs/pilot/feedback-form.md` — 10-question Google Form spec: trust score perception, matching quality, icebreaker usefulness, transcript accuracy, would-use-again likelihood, open-ended feedback.
- `docs/pilot/analytics-events.md` — event spec: `session_started`, `session_completed`, `icebreaker_shown`, `icebreaker_refreshed`, `reported_peer`, `trust_recovery_task_completed`, `transcript_expanded`. Not implemented as code in v1.1 — just specified for v1.2.
- **Report copy (draft):** "Informal pilot conducted 2026-05-05 to 2026-05-10 with n=8 CSUF-adjacent participants. Feedback (Appendix C) informed v1.2 priorities. Not a sanctioned study; no IRB involvement."

**Why this scope:** Real data, honest framing, zero risk of traceability issues.

## 5. Process rules for this work

- **One subproject per commit.** Commit messages reference the subproject letter (e.g. `feat(matching): add MatchScorer (Subproject B)`).
- **No `Co-Authored-By: Claude` lines in commit messages.** Sprint-2 grade flagged this as an anti-pattern. Going forward the commits are authored by Danny alone.
- **Every subproject must have at least one test** where a pure function is plausible (A, B, D, E). C and F are tested via existing integration paths.
- **Traceability:** every subproject commit mentions its Jira ticket. New tickets `TDV-80` through `TDV-86` will be created in Jira before or immediately after each commit.
